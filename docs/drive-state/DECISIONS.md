# Drive state artifact — implementation decisions

Binding decisions taken to make the work dispatchable. Each closes an open
question from `docs/DRIVE_STATE_ARTIFACT.md` §10. **These are the coordinator's
calls, not settled protocol** — every one is reversible before the format is
published to chain, and each is flagged for human review.

| # | Question | Decision | Why, and what it costs |
|---|---|---|---|
| D1 | Section format | ~~JSON, gzipped.~~ → **REVERSED by D12: a SQLite file with a frozen artifact schema, gzipped only below the §2.7 threshold.** The original call follows. **JSON, gzipped.** A top-level object of named sections; section `rows` holds the exported tables. | Dart and TypeScript read it natively with no new dependency, and gzip recovers the verbosity (measured 5.46x end to end: 52.16 MiB to 9.55 MiB). A binary format would be smaller but needs a spec, a codec on both sides, and buys little once compressed. Revisit only if profiling says parse time dominates. |
| D2 | Revision depth | ~~Current state only~~ → **REVERSED. The payload carries `drive_revisions`, `folder_revisions`, `file_revisions` — every revision, not the newest per entity — and `licenses`. `network_transactions` is *derived* on import rather than carried.** | The original reasoning — "covers everything the explorer renders" — was simply false, and I did not check it. `filesInFolderWithLicenseAndRevisionTransactions` (`lib/models/queries/drive_queries.drift:108`), the query the explorer actually uses, **INNER JOINs** `network_transactions` twice through a `file_revisions` subquery. A file with no revision row yields NULL on the ON condition and is dropped. An artifact carrying entries alone would import 41,000 files and show **zero** of them, in every folder — and it would not heal, because the import advances the watermark past the range whose revisions would have satisfied the join. Found by the import audit; verified against the query. Note the size measurement in the proposal (34.63 MiB) already modelled entries **plus** revisions plus network transactions, so this reversal costs nothing against the published numbers — it was D2 that departed from what was measured. Three refinements taken while implementing it. **Depth: every revision.** Measured on the 42k-file drive: 39,878 entities, 1.05 revisions each, 4.7% with more than one, max 4 — so the whole history costs ~5% more rows and keeps what the file details panel shows. **`network_transactions` is regenerated, not serialised.** It is four columns and fully derivable from the revisions, and it has no `driveId`, so publishing it would publish rows about the user's other drives to everyone holding this drive's key; the importer rebuilds it through `lib/sync/utils/network_transaction_utils.dart`, the same helpers sync uses, with one correction — a data transaction lands `confirmed` rather than the helpers' `pending`, because an artifact's coverage claim is the producer's own synced watermark and importing 42,000 pending rows would both paint every file as pending and queue a confirmation query per transaction. **`licenses` travels too.** Its join is a LEFT JOIN, so a missing row hides no file — it silently drops the licence the user attached to their own. `Entity-Count` is unchanged and still counts entities (folders + files + the drive); a revision is a version of an entity, not another one. |
| D3 | Production trigger | **Explicit user action only** in v1. No automatic publishing. | Publishing is permanent, costs money, and must never happen from a sync that reported skipped entities. An explicit action makes that precondition checkable and keeps the safety rail intact. |
| D4 | Who pays | **Whichever upload path the user already has** — Turbo credits or AR. No new payment surface. | Follows the transport-independence rule (§4.4). |
| D5 | Above the 100 MiB payload boundary | **Refuse to produce**, with a clear reason, rather than split. | Multi-part authentication needs its own manifest integrity design. Refusing is honest and safe; a drive that large falls back to snapshots, which is today's behaviour. Deferred, not decided against. **The bound is no longer the cipher's** — see D11. It was justified as an AES-GCM constraint, and the measurement in §2.3 shows AES-GCM holds the *compressed* item (9.55 MiB at 41,767 files), 5.46x less than the number being checked; the public path then removed the cipher from the question entirely. It is kept at the same 100 MiB, re-founded on the **producer's memory** (§2.3: a peak near 950 MiB from a 263 MiB baseline, reached before any cipher is involved and therefore identical for both privacies), and defined as this format's own constant rather than imported from the uploader. One number for both privacies on purpose: two would mean the reader's inflation limit differed by drive, which is a window where a payload is writable by one path and unreadable by another. A test asserts the constant never grows past `maxSizeSupportedByGCMEncryption`, so the private path stays inside GCM's range as a checked consequence rather than an assumption. |
| D6 | ArNS naming | ~~Not wired in v1.~~ → **REVERSED. `LIBRARY_PAGES.md` makes a name the mechanism rather than an acceleration, so the convention is specified there and the apex must become selectable in the existing picker, which drops it today (`assign_name_bloc.dart:92`).** The original call follows. **Not wired in v1.** Discovery is GraphQL by `Entity-Type` + `Drive-Id` + owner. | The ArNS path is the acceleration, not the mechanism, and it depends on an undername convention that needs checking against the ARIO spec. Building discovery behind an interface leaves it a drop-in later. |
| D7 | Export safety mechanism | **SUPERSEDED by D12.** The `INSERT … SELECT` column list that builds the artifact *is* the projection, expressed once in the statement that physically constructs the file, and an unnamed column cannot reach an empty database. The schema-drift test carries over. The original call follows. **Typed projection + schema-drift test** for v1, not database views. | Views need a schema migration on a live database whose fixtures are stale at v19 — the wrong thing to land unattended. A projection naming its columns is functionally equivalent today; the drift test is what makes it hold. **Views remain the target**; this is a deliberate deferral, recorded so it is not forgotten. |
| D8 | Upload | **Built and tested, never executed by the loop.** | Framework safety rail: the loop spends nothing and publishes nothing. |
| D9 | Format version | **Two-component `major.minor`, currently `0.1`**, in both the `State-Version` tag and the payload's `version` field, which must agree. A reader accepts only its own major: newer major refuses as unsupported, older major refuses *explicitly*, any minor within its own major is accepted — **above `1.0`**. While the major is `0` the **minor** is the compatibility unit instead and an exact match is required, because `0.x` says the format is not settled and `0.2` is free to mean what `0.1` would misread. That is the stricter rule and it is what stops an artifact published from one staging build being read by a later build that changed the format underneath it. | The bare integer conflated the two kinds of change §6 exists to separate: with one number, every load-bearing addition locks out every older reader, so the pressure is always to not bump — which is how a three-section payload and a seven-section payload came to share version `1`. Minor covers additive-and-optional, major covers structural. Two components rather than three because there is no bug-fix level for "what fields exist"; it also matches ArFS's own `0.15`. The older-major arm is explicit for a reason found under mutation: a structurally-current payload relabelled `0.9` was **silently imported**, so the arm is not merely cosmetic. Free to introduce now and never again — nothing is published, so there is no migration and no compatibility shim. |
| D11 | Public drives | ~~Out of scope; private-only for v1 (proposal §2.6)~~ → **REVERSED. Public drives publish and read artifacts, on the same chain minus the encryption step: `serialise → gzip → sign as a data item` (the signing step was later removed by D16). `Cipher` and `Cipher-IV` are absent, and their absence is the discriminator. Still format version `0.1` — no bump.** | §2.6's recommendation rested on two arguments and neither survives. **"Public drives have least to gain" is false.** The win (§1.2) is not paying ~420 paginated GraphQL queries and ~42,000 metadata fetches to replay a drive's history, and a public drive pays every one of those identically; what it skips is the per-entity AES decryption, one of three costs per entity and the cheapest of the three to avoid in bulk. The recommendation inverted the size of the win it was weighing. **"A single blob enumerating every name, size and relationship helps an adversary" is already conceded.** A snapshot of a public drive *is* that blob, unencrypted, published today — §2.6 half-admitted this ("snapshots already concede most of this") and recommended against anyway. A public artifact reveals nothing a public drive's snapshot does not. Not "public data is public so nothing matters": aggregation is a real distinction, and the point is that this format does not introduce it. **What replaces the gate is a rail in both directions.** A private drive must never publish in the clear — permanent, irrevocable exposure of every name, size and relationship, and the one failure here that is worse than today's behaviour rather than equal to it — so it is made *unconstructable* rather than checked: `DriveStateProtection` is a sealed type with private constructors whose only factory takes the drive's own `privacy` column with its key, and the unencrypted variant is reachable only through the `public` arm; the codec switches exhaustively over it, so a third variant is a compile error, not a fall-through to the clear. A **reader** refuses any artifact whose cipher-presence contradicts the privacy of the drive it names, in both directions, reported as its own `privacy-mismatch` outcome — following the `Block-Start`/`Block-End` precedent of §3.3 (an untrusted claim checked against a trustworthy one) rather than inventing a second convention. Checked at the tags before the body is touched, again in the codec, which is the layer that decides whether to decrypt, and a third time on the signed payload's own `privacy` field, which matters because the merge writes it onto the local drive row. **No version bump**: nothing is published to chain, so folding public support into `1.0` means there is never a world where some 1.0 readers handle public drives and others do not. Had anything been published this would have been a clean minor bump — a 1.0 reader meets a cipher-less artifact, finds no `Cipher` tag and refuses as malformed, verified — and that fallback is simply not needed. Every other publishing gate is unchanged for a public drive: D3's skip precondition, ownership, write permissions, non-empty, watermark, size. |
| D10 | ArNS records | **`arns_records` and `ant_records` do not travel.** The drive-side fact — which names a file has — is carried in `assignedNames` on `file_entries` and `file_revisions`. | Consistency with the `network_transactions` rule: derived state is regenerated, not carried, and a format that carries one cache but not another is one nobody can reason about. `assignedNames` is a `@JsonKey` field on `FileEntity`, written into and read back from the file's ArFS metadata on chain — so it is authoritative drive content whichever client assigned the name, and it is what the file list and details panel actually render (`data_table_item.dart`, `details_panel.dart`). `arns_records` is read by only the ArNS panel and search, both of which repopulate from ARIO; the residual loss on a restored drive is that search-by-name misses until that refresh. `ant_records` (`domain → process_id`) is public ARIO state with no drive link and should never travel. **Reversible as a minor bump under D9**: the section is optional, so a reader without it still opens the drive and lists every file. That is precisely the case `major.minor` was introduced to make cheap. |
| D12 | The container | **A SQLite file with a frozen artifact schema, not Drift's**, built by `INSERT … SELECT` into an empty attached database and read behind the gate in §2.4. Supersedes D1 and D7. | Measured head to head at 41,767 files on one machine: 5.98 MiB gzipped against 9.55, producer 679 ms against 13,004, import 584 ms against 7,444, and no Dart object per row in either direction. The reasons that outlast the measurements: SQLite publishes a plan to keep its on-disk format backward compatible through 2050 and the US Library of Congress lists it as a recommended storage format for datasets, so the spec is maintained by someone else; every future reader already has a parser (`node:sqlite` in Node, `sql.js` already vendored at `web/sql-wasm.wasm` and loaded since 2022); and a reader can answer a question by touching the pages that hold it, which no JSON container allows and which `LIBRARY_PAGES.md` depends on. The costs are real and accepted: the read gate must be written deliberately, and whether migrating the web database to `drift/wasm.dart` is a prerequisite or a parallel cleanup is the one open implementation question. |
| D13 | Compression | **Every reader accepts both encodings, told apart by the first bytes of the payload** (`1f 8b` for gzip, `SQLite format 3` and a NUL for an uncompressed file). The producer chooses per artifact, and the choice is permanent for that artifact. Producers always compress until Library pages ship; the threshold for publishing a public artifact uncompressed is then set by measurement, with 16 MiB as the starting point. Never a `Content-Encoding` tag. Decided by Phil, 2026-10-14. | §2.7 and §4.5. Compression inside the envelope and transport compression both make byte ranges unreadable, so compressing a large public artifact forecloses page-level reads for ever. A `meta` flag, the earlier form, cannot work: `meta` is inside the compressed bytes it would describe. The bytes carry their own answer, so no tag can lie about it, and the threshold stays adjustable because no reader depends on it. |
| D14 | Snapshots | **Retired on a sequence, not deleted.** Stop nudging private drives now, stop writing one beside every artifact, stop producing once core-js and the CLI read artifacts, and keep the reader for ever. | §11.1. Incremental snapshots and snapshots from ancestors are consequently not worth building, which removes two scoped pieces of work. Retirement is sequenced behind other clients because a snapshot carries each entry's original `gqlNode` and an artifact does not, so the checkable-against-chain property is genuinely lost (§2.5). |
| D15 | Unconfirmed transactions | **The statuses the producer had not confirmed travel, scoped to the drive's own rows, in `transaction_statuses`. A reader makes a listed data transaction `pending` and keeps any other listed transaction `failed`. The producer refuses to publish while a metadata or licence transaction is `pending`. Rows are never dropped for their status. Format `0.2`.** Refines D2's "lands `confirmed`". | D2 had every regenerated transaction land `confirmed`, so an upload that failed arrived as a good file in every client that imported the drive, and nothing re-checked it: the confirmation pass revisits `pending` rows only. That is a false green, permanent per artifact. D2's reason for not carrying statuses was that `network_transactions` has no `driveId`; listing only transactions the drive's own rows reference avoids that. Data becomes `pending` because that is what a sync from GraphQL does with every data transaction, and the confirmation pass resolves a data transaction's owner through its drive, so it is right on attached drives. A metadata transaction is not resolved that way: the pass would ask under the signed-in wallet and fail a good upload on an attached drive, which is why a `pending` one blocks publishing (minutes) rather than travelling. Dropping `failed` rows was rejected: a gateway reports `failed` for a transaction it could not find for long enough, which can be one that is on chain, and dropping it would hide a real file behind an advanced watermark. Every arm mutation-checked. |
| D16 | Authorship | **The payload carries no signature of its own. An artifact's author is the owner of the upload, as the indexer reports it, exactly as for every ArFS entity: discovery queries and filters by the drive owner, and the importer checks it again first (`owner-mismatch`). A private payload is authenticated by AES-GCM under the drive key; a public payload is as trustworthy as the gateway, like that drive's own entities. Decided by Phil, 2026-10-14. Format `0.2`.** Reverses the inner ANS-104 signature of proposal §2.2. | The upload is already a signed data item, but readers cannot check that signature: measured on ardrive.net and turbo-gateway.com for a Turbo-bundled item, no `X-Arweave-Signature` or `X-Arweave-Owner` headers are served and GraphQL returns `"signature": "<not-found>"`; release 75 serves them for bundled items only with `WRITE_ANS104_DATA_ITEM_DB_SIGNATURES=true`, default `false`. The inner signature's only unique property was that the bytes proved their author without any lookup, which nothing in the product uses, while it cost a wallet prompt at publish, routed Wander and ArConnect through the deprecated `arweaveWallet.signature()` with `saltLength: 0` (untested for other verifiers), made core-js and the CLI implement data item verification, and made range reads of a public artifact unverifiable. Independent proof remains available from the upload's own signed data item in its bundle. The cost accepted: a public drive's artifact, and so a hostile SQLite file, can be served by a lying gateway, which the read gate (§2.4) and the decompression bound face in full. Every guard that carries authorship now is mutation-checked: the importer's owner check in both halves, discovery's owner filter, and the private path's encryption. |
| D17 | Identity in the file | **Every artifact carries SQLite `application_id` `0x41724453` (`ArDS`), and a reader refuses a database without it. `meta.producer` names the building client as `<App-Name>/<App-Version>`. `path` and `isGhost` do not travel; a reader writes `''` and false. Decided by Phil, 2026-10-14. Format `0.2`.** | The application id lets a reader, and any SQLite tool, recognise the file from its bytes. The producer is what a reader needs to refuse artifacts from a build with a known defect (delivery plan R4); in the payload it is authenticated on a private drive, where the `App-Version` tag is only what an indexer reports, and it cannot be added after the first publish without a version bump. `path` is written as `''` everywhere and read by nothing; `isGhost` is always false for a vouched row. Dropping both took a 41,767-file drive from about 28 to about 26 MiB. **Considered and not done:** dropping the entry tables (42% smaller); see the delivery plan. |

## Scope boundary for this branch

**In:** export, serialise, compress, encrypt, and the exact inverse;
the ArFS entity and its tags; discovery by GraphQL; import into a sandbox and
merge; sync composition; observability; UI to trigger creation and to show what
a sync used. Tests at every layer.

**Out, deliberately:** executing an upload (D8), ArNS (D6), database views (D7),
multi-part artifacts (D5).

Public drives were on this list and are not any more; see D11.

## Non-negotiables for every lane

1. **No key material may leave the database.** `profiles` is never read.
   `drives` is read column-wise, excluding `encryptedKey`, `driveKeyGenerated`,
   `keyEncryptionIv`. A test must fail if the schema grows a column the
   projection would pick up.
2. **Every failure is a fallback.** No path may fail a drive because an artifact
   was bad. Unknown version, wrong owner, failed decrypt, count mismatch —
   log an enumerated reason and sync normally.
3. **No regressions.** The full suite is the gate, not the touched files.
4. **Nothing is uploaded, published, tagged or released by any agent.**
